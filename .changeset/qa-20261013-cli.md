'@loopress/cli': patch
---

`lps snippet push` keeps an HTML snippet's inline `<?php ... ?>` block instead of stripping it, keeps the description from the snippet's `.json` file instead of replacing it with "Imported from <path>", and skips, with a failed push, every file whose id another file also uses, instead of letting the last one silently overwrite the other on the site. `lps diff` now shows a removed `<?php` on a non-PHP snippet as drift. `lps validate` accepts the `{"version", "active"}` plugin pin `lps plugin pull` writes for an inactive plugin. `lps promote` takes `--overwrite`, passed to its push, and says the local files may already hold part of `<from>` when its pull fails. `lps hook list` says "an action", and `lps doctor` no longer repeats "failed to load". `lps push` skips snippets on a project with no `snippets/` directory instead of ending on an ENOENT error. `lps form push` writes the id WordPress assigned into a new form's file, so the next push updates that form instead of creating a duplicate. `lps theme version pull` skips a theme with no version, the Loopress child theme included, instead of pinning it to an empty version `lps theme version push` then fails on. `lps plugin audit` reads the affected version range wpvulnerability.net actually returns (`operator`), so it no longer reports every advisory ever published for a plugin, audits a `latest` pin as the newest WordPress.org release, decodes HTML entities in advisory names, and keeps its `--json` output when it exits with 1. `lps composer push` names the WordPress.org plugins and themes the site has and composer.json lacks, which the push uninstalls, on a dry run too, and asks before uninstalling them in a terminal. `lps pull` (and so `lps promote`) skips ACF, forms and snippets, instead of failing, on a site without the plugin they need when the project has no directory for them.
